# 후기돋보기 데이터 저장과 수집

2026-11-07 기준.

## 지금의 구성

기존에는 `.cache/catalog/`의 HTML·JSON 원문과 `data/`의 공개 JSON으로만 관리했다. 이제 원문 저장·중복 방지·수집 이력은 로컬 SQLite DB가 맡는다.

```text
상품·리뷰·블로그 수집
        ↓
.local-data/review-magnifier.sqlite3
        ↓ 검토된 제품·요약·원문 발췌만 내보내기
data/catalog.json → 화면 빌드 → docs/ → GitHub Pages
```

SQLite 파일은 실제 DB이며 별도 서버가 필요 없다. 초기 수집과 로컬 분석에 사용한다. 팀원이 동시에 쓰는 운영 서비스 단계에서는 백엔드와 공유 PostgreSQL 등으로 옮길 수 있다. 현재 GitHub Pages는 정적 파일만 제공하므로 DB 서버나 수집기를 실행하지 않는다.

DB·원문 캐시·비밀키는 GitHub와 배포 폴더에 포함하지 않는다. 로컬 미리보기도 `docs/`만 제공한다. `file://`이나 프로젝트 폴더 전체를 웹 서버로 여는 방식으로 원문 DB를 제공하지 않는다.

## 보관하는 데이터

| 구분 | 테이블 | 의미 |
|---|---|---|
| 검토된 제품 | `products` | 현재 사이트의 제품 모델 |
| 판매처·쇼핑 상품 후보 | `listings` | 출처별 상품 ID. 검토 전에는 기존 제품에 자동 연결하지 않음 |
| 가격·평점·전체 리뷰 수 | `listing_observations` | 시점별 관측값. 데이터가 없으면 빈 값 유지 |
| 구매 후기 | `reviews`, `review_versions` | 출처별 리뷰 ID와 원문 변경 이력 |
| 블로그 후보·본문 | `documents`, `document_versions` | 구매 후기와 분리. 검색 설명은 본문으로 취급하지 않음 |
| 요약·발췌·언급 근거 | `public_summaries`, `public_excerpts`, `review_topics`, `review_mentions` | 원문의 특정 버전과 연결 |
| 수집 진행 | `collection_jobs`, `collection_runs`, `collection_pages` | 검색어·다음 위치·실패·요청 수·원본 응답 해시 |
| 후보 연결 | `search_hits` | 어떤 검색에서 찾았는지 기록. 모델 일치 여부는 `unreviewed`부터 시작 |

리뷰는 `(판매처 상품, 리뷰 ID)`, 상품은 `(출처, 상품 ID)`, 블로그는 `(출처, 정규화한 글 ID)`로 중복을 방지한다. 원문이 바뀌면 새 버전을 남긴다. 기존 공개 제품의 원문이 바뀌면 예전 요약·횟수를 자동으로 재사용하지 않고 내보내기를 중단한다.

블로그의 광고 관련 문구를 찾으면 위치를 저장한다. 발견하지 못한 경우는 `unknown`이며 비광고 인증이 아니다. 블로그의 제목에 `내돈내산`이 있어도 검증된 구매 후기로 표시하지 않는다.

## 현재 실제 확보 범위

- 기존 검토 제품 12개, 판매처 구매 리뷰 원문 113개, 요약 36개, 승인된 원문 발췌 36개를 DB로 이전했다.
- 네이버 블로그 검색 1회에서 후보 10개를 확보했고 그중 선택한 글 3개의 본문을 로컬 DB에 저장했다. 나머지 7개는 검색 메타데이터만 있다.
- 32개 검색어에 쇼핑·블로그 각각을 연결한 64개 공식 API 작업을 준비했다. 아직 실행 전이다. 작업이 있다는 것이 새 제품·후기를 확보했다는 뜻은 아니다.
- 네이버 쇼핑 공개 검색의 소량 확인은 HTTP 418로 제한됐다. 우회·반복 요청을 하지 않았다.
- 검색 결과에는 다른 세대 제품·광고·비교글이 섞일 수 있다. 새 후보는 현재 사이트의 집계에 합치거나 공개하지 않았다.

## 네이버 API 준비

1. [네이버 개발자센터](https://developers.naver.com/apps/#/register)에서 애플리케이션을 등록한다. 이용 API는 **검색**을 선택한다. 약관 동의·계정 등록은 사용자가 직접 진행한다.
2. Client ID와 Client Secret을 발급받는다.
3. `.env.example`을 참고해 프로젝트에 비공개 `.env`를 만들고 아래 두 값을 설정한다. 채팅·GitHub·브라우저 코드에는 넣지 않는다.

```dotenv
NAVER_SEARCH_CLIENT_ID=발급받은_ID
NAVER_SEARCH_CLIENT_SECRET=발급받은_시크릿
```

4. `npm run db:doctor`로 값의 존재 여부만 확인한다. 실제 값은 출력하지 않는다.
5. 처음에는 `npm run data:collect -- --max-requests 2`로 실제 API 접근을 확인한다.

[네이버 쇼핑 검색 API](https://developers.naver.com/docs/serviceapi/search/shopping/shopping.md)는 상품 메타데이터를 제공하며 구매 후기 본문을 제공하지 않는다. [블로그 검색 API](https://developers.naver.com/docs/serviceapi/search/blog/blog.md)는 제목·URL·설명 문구를 제공하며 글 전체 본문은 아니다. 공식 문서상 한 번에 최대 100개, 시작 위치 최대 1000이며 검색 API 호출 한도는 하루 25,000회다. 이 한도는 앱 전체가 공유하므로, 현재 수집기는 로컬 실행당 최대 1000회·기본 20회, 로컬 하루 1000회로 더 작게 제한한다.

검색은 전체 상품 목록을 순회하는 API가 아니다. 검색어별 제한 범위의 후보를 쌓는 방식이며 **모든 상품·모든 리뷰를 확보했다고 표현하지 않는다.** 쇼핑 구매 리뷰 전체는 해당 판매처의 허용된 데이터 제공 경로나 별도 권한이 있어야 추가할 수 있다.

`config/naver-seeds.json`에서 검색어를 추가할 수 있다. 각 검색어의 상품은 서로 중복될 수 있고 최대 검색 위치에 도달하면 검색 결과가 더 있어도 해당 작업은 종료된다. 블로그 전체 본문의 반복 수집은 현재 공식 검색 작업에 연결하지 않았다. 본문 확인은 선택한 문서 ID를 지정한 소량 파일럿만 지원한다.

## 명령

```sh
npm run db:init
npm run db:migrate
npm run db:stats
npm run db:doctor
npm run db:backup
npm run data:plan
npm run data:collect -- --max-requests 20
npm run db:export
npm run test:data
npm run build
```

- `db:migrate`는 기존 로컬 캐시를 가져오는 명령이다. 새 환경에 원문 캐시가 없으면 원문을 복원한 것처럼 표시하지 않는다.
- `data:collect`는 공식 API 키가 있어야 실행한다. 성공한 페이지의 저장과 다음 위치 갱신은 하나의 트랜잭션으로 처리한다. 중단되면 다음 실행에서 이어간다.
- 401·403·418·429 응답은 해당 작업을 `blocked`로 기록하고 배치를 중단한다. 원인을 해결한 뒤 `--retry-failed`로 재개할 수 있다. 키가 없거나 오류가 난 것을 성공 0건으로 표시하지 않는다.
- `db:backup`은 SQLite 백업 기능으로 일관된 복사본을 `.local-data/backups/`에 만든다. 파일명 중복이면 덮어쓰지 않는다.
- DB가 있으면 빌드는 DB의 검토된 자료를 사용한다. DB가 없는 팀원 환경은 기존 공개 스냅샷으로 빌드할 수 있다.
- `db:export`는 검토된 12개 제품과 승인된 짧은 발췌만 내보낸다. 신규 후보나 원문 전체를 포함하지 않는다.

현재 저장소 구성은 수집·연구용 첫 단계다. 팀 공용 운영 DB, 서버 API, 모델 매칭 검수, 구매 리뷰 공급 경로와 정기 수집 운영은 다음 단계로 남아 있다.
