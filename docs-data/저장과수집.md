# 후기돋보기 데이터 저장과 수집

2026-11-07 기준.

## 지금의 구성

기존에는 `.cache/catalog/`의 HTML·JSON 원문과 `data/`의 공개 JSON으로만 관리했다. 이제 원문 저장·중복 방지·수집 이력은 로컬 SQLite DB가 맡는다.

```text
상품·리뷰·블로그 수집
        ↓
.local-data/review-magnifier.sqlite3
        ↓ 검토된 제품·요약·원문 발췌만 내보내기
data/catalog.json → 화면 빌드 → docs/ → GitHub Pages
```

SQLite 파일은 실제 DB이며 별도 서버가 필요 없다. 초기 수집과 로컬 분석에 사용한다. 팀원이 동시에 쓰는 운영 서비스 단계에서는 백엔드와 공유 PostgreSQL 등으로 옮길 수 있다. 현재 GitHub Pages는 정적 파일만 제공하므로 DB 서버나 수집기를 실행하지 않는다.

DB·원문 캐시·비밀키는 GitHub와 배포 폴더에 포함하지 않는다. 로컬 미리보기도 `docs/`만 제공한다. `file://`이나 프로젝트 폴더 전체를 웹 서버로 여는 방식으로 원문 DB를 제공하지 않는다.

## 보관하는 데이터

| 구분 | 테이블 | 의미 |
|---|---|---|
| 검토된 제품 | `products` | 현재 사이트의 제품 모델 |
| 판매처·쇼핑 상품 후보 | `listings` | 출처별 상품 ID. 검토 전에는 기존 제품에 자동 연결하지 않음 |
| 가격·평점·전체 리뷰 수 | `listing_observations` | 시점별 관측값. 데이터가 없으면 빈 값 유지 |
| 구매 후기 | `reviews`, `review_versions` | 출처별 리뷰 ID와 원문 변경 이력 |
| 블로그 후보·본문 | `documents`, `document_versions` | 구매 후기와 분리. 검색 설명은 본문으로 취급하지 않음 |
| 요약·발췌·언급 근거 | `public_summaries`, `public_excerpts`, `review_topics`, `review_mentions` | 원문의 특정 버전과 연결 |
| 수집 진행 | `collection_jobs`, `collection_runs`, `collection_pages` | 검색어·다음 위치·실패·요청 수·원본 응답 해시 |
| 후보 연결 | `search_hits` | 어떤 검색에서 찾았는지 기록. 모델 일치 여부는 `unreviewed`부터 시작 |

리뷰는 `(판매처 상품, 리뷰 ID)`, 상품은 `(출처, 상품 ID)`, 블로그는 `(출처, 정규화한 글 ID)`로 중복을 방지한다. 원문이 바뀌면 새 버전을 남긴다. 기존 공개 제품의 원문이 바뀌면 예전 요약·횟수를 자동으로 재사용하지 않고 내보내기를 중단한다.

블로그의 광고 관련 문구를 찾으면 위치를 저장한다. 발견하지 못한 경우는 `unknown`이며 비광고 인증이 아니다. 블로그의 제목에 `내돈내산`이 있어도 검증된 구매 후기로 표시하지 않는다.

- 계정 없는 새 경로로 상품 페이지 3곳과 블로그 RSS 3곳을 실제 확인했다. 에어팟 구매 리뷰 10개와 RSS 관련 글 2개는 기존 자료와 중복돼 증가량이 0개다. 소니 WH-1000XM6와 갤럭시 버즈3 프로의 판매처 상품 2개를 새 후보로 저장했다. 소니 판매 페이지의 리뷰 수는 0개다. [버즈3 프로 판매 페이지](https://www.11st.co.kr/products/8201640764)는 전체 리뷰 수 6개를 표시했고 첫 HTML에 노출된 원문 2개를 실제 확보했다. 검색 목록의 리뷰 수와 상세 페이지의 값이 달라, 상세 페이지에서 직접 관측한 값과 수집 시각을 기록했다.
- 이 파일럿 시점의 DB는 검토된 제품 12개·판매처 상품 14개·구매 리뷰 원문 115개·블로그 후보 10개(본문 3개)다. 공개 사이트는 검토된 12개 제품과 기존 113개 리뷰 표본을 계속 사용한다. RSS 88개 항목 중 무관한 글은 후보로 저장하지 않았다.
- 동일 명령 재실행 시 네트워크 요청 0회와 증가량 0개를 확인했다. 신규 원문을 수집한 것처럼 표본 수를 늘리지 않았다.

## 계정·API 키 없이 진행하는 경로

현재 Naver Cloud 계정은 ‘서비스 이용이 불가능한 계정’ 안내로 콘솔 접근이 막혀 있다. 데이터 수집의 다음 단계가 계정 해결에 의존하지 않도록 **지정 상품의 공개 페이지 + 지정 블로그의 RSS** 경로를 추가했다. 결제수단 등록이나 다른 계정 생성은 필요하지 않다.

```sh
npm run data:products
npm run data:rss
npm run db:stats
```

대상은 `config/public-sources.json`에서 지정한다.

- `products`: `https://www.11st.co.kr/products/상품번호` 형식의 URL. 첫 공개 HTML에 들어 있는 상품 정보와 리뷰만 읽는다. 로그인, 리뷰 전체 페이지 순회, 비공개 API 호출을 하지 않는다. 원문의 HTML 태그를 풀고 문장·맞춤법·내부 공백과 줄바꿈을 유지한다. 페이지 전체 리뷰 수와 실제 확보한 표본 수를 따로 기록한다.
- `blogs`: `https://rss.blog.naver.com/블로그ID.xml` 형식의 RSS URL과 `titleKeywords`. 제목에 키워드가 있는 글의 제목·링크·발행일·RSS 설명만 후보로 저장한다. 키워드 일치는 제품 모델 검증이 아니며 모든 후보는 검토 전 상태다. RSS 설명을 글 전체 본문이나 구매 후기 원문으로 저장하지 않는다. [네이버 공식 RSS 안내](https://help.naver.com/service/5593/contents/24722?lang=ko&osType=COMMONOS)는 HTTPS와 HTTP/1.1 이상을 사용하도록 안내한다.

이 경로는 **작은 공개 자료 표본의 수집·연구**를 위한 것이다. RSS는 특정 블로그가 공개한 최근 글 목록으로, 네이버 전체 검색이나 과거 글 전량 제공 기능이 아니다. 전체 상품·리뷰를 지속 공급하는 운영 서비스에는 별도 공급 협의나 이용 가능한 데이터 제공 경로가 필요하다.

RSS는 대상·요청 최대 3곳, 상품은 최대 12곳이다. 기본 요청 수는 3회이며 두 명령 합산 UTC 하루 24회로 제한한다. 생필품 8종 추가 요청에 맞춰 상품 수집 한도만 늘렸고, 블로그 소량 검증 한도는 유지한다. 같은 URL은 6시간 이내 재요청하지 않는다. 성공한 응답은 해시를 확인한 비공개 캐시를 사용하며 수집 시각을 현재 시각으로 바꾸지 않는다. 차단·로그인 페이지·지원하지 않는 HTML·잘못된 RSS는 중단하고 이력을 남긴다. 우회나 즉시 재시도는 없다. `request_limited`, `budget_limited`, `cooldown`은 해당 제한 때문에 새 요청을 하지 않았거나 중단한 상태다. 실행 결과의 `records`는 관측 레코드 수이며 신규 증가량은 `newReviews`·`newBlogCandidates`·`newListings`를 확인한다.

상품·리뷰는 기존 출처 ID로 중복을 제거하고, 달라진 원문만 새 버전을 만든다. 신규 판매처 상품은 `product_id`를 비워 두고 기존 제품 모델에 자동 연결하지 않는다. 기존 공개 제품에 새 리뷰나 변경 원문이 들어오면 요약·언급 수를 다시 검토하기 전까지 공개 내보내기가 중단된다. 블로그 후보는 구매 후기 표본이나 긍정·부정 횟수에 자동 포함되지 않는다.

원문 응답은 `.local-data/raw/public-pages/`에, 수집 시각·응답 해시·캐시 여부·발견한 글 ID는 DB의 `metadata`, `collection_runs`, `collection_events`에 저장한다. DB·원문·키는 공개 저장소 및 GitHub Pages에 포함하지 않는다.

## 네이버 API HUB 준비 (선택 사항)

**기존 개발자센터의 신규 신청 안내는 현재 적용되지 않는다.** [네이버 공식 이관 공지](https://developers.naver.com/notice/article/32530)에 따르면 2026-07-31부터 검색 API 신규 신청은 NAVER API HUB에서만 가능하다. 쇼핑·책·전문자료 검색은 같은 날 종료됐으며 HUB 이관이나 별도 대체 API가 없다. 따라서 이번 준비는 **블로그 검색**만 대상으로 한다. 쇼핑 인사이트는 클릭 추이 서비스로 상품 목록이나 구매 리뷰 API가 아니다.

1. [네이버 클라우드 플랫폼 콘솔](https://console.ncloud.com/)에 로그인한다. 계정이 없다면 회원가입·본인 인증·약관 확인은 사용자가 직접 진행한다.
2. **All Services > Application Services > NAVER API HUB > Subscription**에서 이용 신청을 확인한다. 개인정보 제공·약관·결제수단·유료 상품 관련 선택은 사용자가 내용을 확인하고 결정한다.
3. **Application > Application 등록**에서 NAVER 검색의 **블로그**를 선택한다. 다른 서비스는 신청하지 않는다.
4. Application 이름은 **review-magnifier**로 준비한다. 공식 안내에 따르면 이름은 최대 20자이며 영문·숫자·하이픈을 사용할 수 있다. 이전 개발자센터의 WEB·URL 입력 절차를 그대로 적용하지 않는다.
5. 최종 등록과 키 발급을 사용자가 완료한 뒤 인증 정보의 Client ID와 Client Secret을 프로젝트의 비공개 `.env`에 설정한다. 채팅이나 스크린샷에 키를 노출하지 않는다.

```dotenv
NAVER_API_HUB_CLIENT_ID=발급받은_HUB_ID
NAVER_API_HUB_CLIENT_SECRET=발급받은_HUB_시크릿
```

6. `npm run db:doctor`로 설정 여부만 확인한다. 실제 값은 출력하지 않는다.
7. 현재 요금·서비스 이용 조건과 호출 한도를 콘솔에서 확인한 뒤 처음에는 `npm run data:collect -- --max-requests 2`로 접근을 검증한다. 코드의 로컬 제한은 실행당 최대 1000회·기본 20회, UTC 날짜 기준 하루 1000회이며 네이버 서비스 전체의 잔여 한도를 뜻하지 않는다.

공식 문서: [이용 신청·Application 등록](https://guide.ncloud-docs.com/docs/apihub-application), [블로그 API](https://api.ncloud-docs.com/docs/naver-api-hub-search-blog), [인증 헤더](https://api.ncloud-docs.com/docs/naver-api-hub-overview).

호출 주소는 `https://naverapihub.apigw.ntruss.com/search/v1/blog`, 형식은 `format=json`이다. 인증은 `X-NCP-APIGW-API-KEY-ID`·`X-NCP-APIGW-API-KEY`를 사용한다. 기존 개발자센터 키를 HUB 키로 자동 재사용하지 않는다. 구형 변수 `NAVER_SEARCH_CLIENT_ID`·`NAVER_SEARCH_CLIENT_SECRET`만 설정하면 수집은 실행되지 않는다.

블로그 검색은 제목·URL·검색 설명을 제공하며 글 전체 본문이 아니다. 검색 설명을 실제 후기 원문으로 저장하지 않는다. 검색은 전체 상품 목록을 순회하는 API가 아니며 **모든 상품·리뷰를 확보했다고 표현하지 않는다.** 상품 정보와 구매 리뷰 확보 경로는 별도로 검토해야 한다.

`config/naver-seeds.json`에서 블로그 검색어를 추가할 수 있다. 같은 글이 여러 검색에서 나올 수 있으며 중복을 제거한다. 블로그 본문의 반복 수집은 API 작업에 자동 연결하지 않았고, 확인할 문서 ID를 지정한 소량 파일럿만 지원한다.

## 명령

```sh
npm run db:init
npm run db:migrate
npm run db:stats
npm run db:doctor
npm run db:backup
npm run data:products
npm run data:rss
npm run data:plan
npm run data:collect -- --max-requests 20
npm run db:export
npm run test:data
npm run build
```

- `db:migrate`는 기존 로컬 캐시를 가져오는 명령이다. 새 환경에 원문 캐시가 없으면 원문을 복원한 것처럼 표시하지 않는다.
- `data:collect`는 NAVER API HUB의 블로그 권한과 키가 있어야 실행한다. 성공한 페이지의 저장과 다음 위치 갱신은 하나의 트랜잭션으로 처리한다. 중단되면 다음 실행에서 이어간다.
- 401·403·418·429 응답은 해당 작업을 `blocked`로 기록하고 배치를 중단한다. 원인을 해결한 뒤 `--retry-failed`로 블로그 작업을 재개할 수 있다. 서비스가 종료된 쇼핑 검색은 이 옵션으로도 재개하지 않는다. 키가 없거나 오류가 난 것을 성공 0건으로 표시하지 않는다.
- `db:backup`은 SQLite 백업 기능으로 일관된 복사본을 `.local-data/backups/`에 만든다. 파일명 중복이면 덮어쓰지 않는다.
- DB가 있으면 빌드는 DB의 검토된 자료를 사용한다. DB가 없는 팀원 환경은 기존 공개 스냅샷으로 빌드할 수 있다.
- `db:export`는 검토된 12개 제품과 승인된 짧은 발췌만 내보낸다. 신규 후보나 원문 전체를 포함하지 않는다.

현재 저장소 구성은 수집·연구용 첫 단계다. 팀 공용 운영 DB, 서버 API, 모델 매칭 검수, 구매 리뷰 공급 경로와 정기 수집 운영은 다음 단계로 남아 있다.

## 2026-11-07 생필품 확장

사용자 요청으로 생필품 8종을 추가했다. 실제 표본은 화장지 9개·키친타월 6개·물티슈 2개·세탁세제 5개·샴푸 8개·치약 옵션 모음 10개·위생백 2개·주방세제 5개로 총 47개다. 광고성·일반적 효능 문구를 사용 경험으로 확대하지 않았고, 없는 부정 의견은 만들지 않았다. 부정 의견이 없는 품목은 빈 상태를 표시한다.

공개 대상은 제품 20개·표본 160개·요약 58개·발췌 58개다. DB 전체는 판매처 상품 27개·리뷰 원문 164개이며, 미검토 후보 및 제외한 판매 페이지 자료 4개는 공개하지 않는다. `npm run data:products -- --config config/household-sources.json --max-requests 8`로 같은 명시적 상품 페이지를 확인할 수 있다. 새 원문이 들어오면 공개 요약 재검토가 필요하다.
